# Security

## When to use it
After the data model, the API design and the UI design (04–06), before Planning: security checks what they decided, so the tables, the endpoints and the flows must exist. It needs the PRD's security requirements and non-goals, the system design's containers, providers, data map, deployment and monitoring, compliance's DPIA, breach plan, processors and retention, the architecture's shared rules (login, permissions, errors, logs), stack, testing, repository and maintenance, the data model's tables with personal and health data marked, the API's map (who may call each endpoint, which ones are limited) and error catalog, and the UI's flows with their failure paths. Plus everything 01–06 left "for Security". **Before the first line of code:** a protection decided now is a rule every slice follows; one found after launch is a fix across the code, maybe after the data has already left.

Then once per slice in Build (`/security slice <n>`): a short pass over what the slice brings in, and its protections proven; and again before the first tester and before launch, as a checklist, like compliance.

At work: a feature that touches login, money, personal data or uploaded files; a new provider or integration (a webhook, a sign-in with Google); a big customer's security questionnaire, or a request for ISO 27001 or SOC 2; a pentest report; a critical vulnerability in a library used everywhere (Log4Shell, December 2021); after an incident; a code review of a new endpoint. Also in the first days at a new company: the threat model (if one exists), how login works, where the secrets live and who can reach production tell you quickly how mature the product is.

## The problem it solves
Steps 01–06 decided many protections, each in its place: a session in an `HttpOnly` cookie, passwords hashed with Argon2id, 404 for someone else's item, every endpoint closed unless it says who may use it, 429 on too many attempts, secrets only on the server, a secret scan before a commit. No document looked at the whole system as an attacker would: what's worth stealing (a person's weight and log, the admin's account, the keys), where you get in (every endpoint, a payment provider's webhook, the links in emails, an uploaded photo, CI, the hosting account), what happens when a single protection fails, and how you find out someone is trying. And the numbers stayed open: how long a session lasts, how many login attempts, 8 or 15 characters, how long a reset link works.

Without an answer, each protection is decided by the first PR that needs it, and the holes sit between PRs: a new endpoint without the "is it yours?" check (first in the OWASP API Security Top 10); a compromised npm package running on the laptop and in CI; the admin's account with a password leaked from another site, changing shared data for everyone; a GitHub account without a second factor, which opens everything. And a user finds out first.

Security decides **what is protected, from whom, how, and how each protection is proven**: the assets and the realistic attackers, the map with its trust boundaries, the threats on every flow, each one's protection with its numbers, the shared protections (headers, keys, the database's users, dependencies, CI, the providers' accounts), what's logged and what raises an alert, and the tests that prove each protection, automatically and by hand.

## How to run it
- **The bar:** do what a senior security engineer or the CTO of a well-run company would accept, in the simplest form that meets it. Use the real industry method and name it (STRIDE, OWASP ASVS, NIST SP 800-63B), so the user learns it. Say what you leave out and why.
- **Teach while you go, starting from the problem.** The user may be a frontend developer with no backend experience. **Before any tool, file or check, say what problem it prevents, in a situation a frontend developer has lived** (a token put in `localStorage` "just for now"; an `.env` pushed by mistake; a Dependabot PR ignored for months; a CORS error that turned out to be a protection). Only then how it works; a "why" gets one sentence of purpose, never more "how". Every term gets one line on what it is, compared with something a frontend developer knows: React escaping text in JSX is already an XSS defence; an `HttpOnly` cookie is already a session no script can read; `pnpm audit` is already a dependency scan; a CSP error in the console is already a security header at work. **At a technical chunk, plain words and one example with numbers come first** (a password of 8 mixed characters has about 95⁸ ≈ 6.6 × 10¹⁵ combinations, one of 15 random lowercase letters about 26¹⁵ ≈ 1.7 × 10²¹), then what it means for the user; the tables after, or only in the file.
- **One step per message, and big steps in chunks.** Show a step, wait for the user's OK, then the next. Steps 4 and 5 are big: one area or one sub-topic per chunk; **count the chunks before announcing them**; save and commit each chunk once it's confirmed, **added to its file, never by rewriting the file** (`>>`, not `>`).
- **Ask only when there's a real choice.** When all the arguments point one way and no realistic alternative fits, write it as decided, with its arguments, and move on. Ask when there are at least two options the user could reasonably pick; once chosen, the choice is final. When the user voices a fear or a doubt next to a choice, resolve it before recording the decision.
- **Show another step's exact text in the same message as the decision.** When a choice will change the PRD, compliance, the API or the UI, the message that asks it already holds the exact before-and-after of each line it touches; a yes then covers both, without a second round only to approve the wording. Found on the first run: a dozen extra rounds for texts that were mere consequences.
- **Before recommending, weigh two things besides the technique:** what most of the industry does, and what serves the user's purpose (what they'll meet at work counts as a real argument). When the options are technically equal, say so first. Change a recommendation only for a new fact, and name the fact.
- **Weigh the owner's budget before proposing a paid service.** A product without revenue doesn't get a €5,000 pentest or a paid scanner as a real option: lead with what's free (our own tests, open-source scanners, an active scan on our own staging) and name the paid one only as "later", with the trigger that brings it back (revenue, a B2B customer, a big change).
- **Every number with its argument:** a known standard (named, its official page checked on the web), a target set earlier (cited), or a guess marked `[ASSUMPTION]` with its reasoning and how it will be tuned (a table of limits and the alerts' thresholds are tuned in the beta, on what's seen); the README's open questions gather the step's assumptions in one row, with the moment they're tuned. For a choice, an argument card: why; the main alternative and who uses it; when the alternative is better; what someone may answer, and the reply; the source. When the industry is split (SameSite alone or a CSRF token; Row-Level Security or filters in the code), name the camps. Why: the user must be able to defend each choice in a security review or a customer's questionnaire.
- **Every real choice as lettered options, dated.** A and B (sometimes C), each with its card; the user picks, and the file and the journal keep the letter and the date ("option A, 2026-11-09"), with what B would have meant, so a later reader sees what was set aside.
- **Where the documents are:** the `Project documents:` line in `CLAUDE.md` gives the documents folder; without it, use `docs/` in the current folder. Write into `docs/02-design/07-security/` and the ADRs into `docs/00-project/adr/`; create them if they don't exist.
- **Read first:** the PRD (`docs/01-discovery/04-prd.md`: the security requirements, the roles, the non-goals), the system design (`docs/02-design/01-system-design/`: containers, data, providers, deployment, monitoring, failures), compliance (`docs/02-design/02-compliance/`: the record, the processors, retention, the DPIA, the breach plan), the architecture (`docs/02-design/03-architecture/`: the shared rules, the stack, testing, the repository, maintenance), the data model (`docs/02-design/04-data-model/`: the tables with personal and health data marked, the one-time links, the sessions, the lifecycle), the API design (`docs/02-design/05-api-design/`: the map with who may call each endpoint and which are limited, the error catalog, `openapi.yaml`), the UI design (`docs/02-design/06-ui-design/`: the flows and their failure paths), and the ADRs. **Search every earlier folder for "Security" and "07"** and gather everything left for this step in one list, each item with where it came from. Ask only what's missing.
- **An existing app is a source of facts, not a model.** Read it for the headers it sends, how it keeps sessions, which accounts reach production. A gap in an internal app isn't treated as a live incident unless the user says so.
- **The protections decided in 01–06 aren't decided again.** Here they're gathered, seen together and proven. If one is wrong or missing, stop, say so, and on a yes fix it where it lives, with a journal line. **The same for the PRD and compliance:** any change, even a number that only closes a gap, is shown to the user first with its exact text. **And the other way:** when a later step (the AI design, the monitoring, a later review of the files) brings a key, a provider, an address or a flow, this folder is corrected in place, the date in the sentence ("corrected 2026-11-09: it said …"), a journal line, and the counts run again.
- **Defence only.** Checks run on the user's own local copies and their own staging, never on someone else's systems; a scanner that attacks (ZAP's active scan) only with the user's yes, on the user's address. **No secret in the documents:** write where a key lives, what it opens and who can read it, never its value.
- **The whole threat model in Design** (chosen on 2026-10-16). The purpose in one sentence: **a threat found before the code changes a contract nobody has built yet, so it costs minutes.** Every flow of the MVP goes through step 4 now, because the API design already wrote every endpoint; in each slice, `/security slice <n>` only passes over what's new or changed and proves the slice's protections. Why: unlike screens, endpoints don't change after the tests with people; OWASP's Threat Modeling Cheat Sheet: "ideally performed early in the SDLC, such as during the design phase", then "maintained, updated and refined alongside the system". The alternative (the riskiest flows now, the rest per slice, as the UI design does for screens) wins when the API is written sprint by sprint with no map ahead, which is most agile teams.
- **The bar is OWASP ASVS, its level chosen per product** (decided): the only standard with verifiable requirements on levels; customers' questionnaires and pentests at work map to it. The OWASP Top 10 is an awareness list, used at step 4 so no category is forgotten.
- **The model lives in markdown, in the repository, with the map drawn from text** (decided): two forms, each with its reader: the markdown for people, with the why of every choice, read in a PR like every earlier step; the scripts in `checks/` for programs (the count of ways in, which fails when an endpoint of `openapi.yaml` is missing from the model; the hash's timing; the CSP in a real browser, the scanners on their planted cases). At work, OWASP Threat Dragon, Microsoft's Threat Modeling Tool or IriusRisk where the team already uses them.
- **Try the decisions now, as the data model ran its schema on a real database:** Row-Level Security on a real PostgreSQL with the app's user (if chosen), the password hash's time on the server's size, the CSP on the UI design's pages (served with the header, zero violations in the console), a query to the leaked-password service with a test hash. **Write "tried" only for what a test proved, and "not run" for what didn't,** with why and when it runs (a scanner not installed on the laptop today runs in slice 1, on the version of the day); keep every script in `checks/`. **A check is tried on planted mistakes first** (a fake key for the secret scanner, made at run time so the repository holds none; a library version with a known vulnerability; a missing header; an endpoint without an access rule), one per rule, and on a clean case **doing what the real app does**, where nothing must be found (the CSP's clean page registers the service worker, as the app will): **a check that has never failed proves nothing.** A tool downloaded for the check is named with its size and asked for first. **Where a framework's documentation is vague, read its source,** and write "read in its source" with the date.
- **Anything new in the middle of the step goes through the whole model at once.** A new address (a list of the person's sessions, an endpoint for the app's errors), a new outside call (a leaked-password service, a secrets vault) or a new table added at step 7 or 12 gets, in the same chunk: its STRIDE rows in the threats, its flow on the map (redrawn), its row in the table of limits, and the ways-in script run again with every count updated where it's written. Found on the first run: the separate check found two flows missing from the map and a feature never asked STRIDE.
- **Every threat traceable, from its row to its proof.** An id is never reused: a new threat takes the next free number, even when one in the middle was never used or a draft took an id already taken. **Every threat that isn't only accepted or transferred has its check named in a row of `11-checks.md`**, and a script lists the threats' ids against the ones 11-checks names, the accepted and transferred ones listed apart (found when the first run's files were walked through: a third of the threats were named in no row, so their checks existed only as words in the threats' table). Every accepted risk has its reason, who accepted it, the date and the event that reopens it, in the README.
- **A deviation is not a gap.** A deviation is a requirement not met on purpose: its reason, what stands in its place, who accepted it, when it's revisited, in the README's accepted risks. A gap is one nobody had covered: its rule for Build, its test and the slice that carries it. **A gap stays a gap until the code meets it,** even once its rule is written; and a reviewer's or an agent's "gap" is a hypothesis until it's found missing in the file it names.
- **The journal speaks in one voice, the user's, and is never rewritten.** One dated line per decision or change: the step and the chunk, who decided and with which option, what was set aside, what a script counted again, which other files changed with it. A later correction is a new line; the corrected sentence keeps its old value in a "(corrected <date>: it said …)" note. Found when the first run's files were walked through: "chosen by [the user's name]" and "with my yes" mixed in one journal, put in one voice afterwards.
- **The AI as a provider is here; the AI's prompts are not.** This step covers the AI's key, its budget, what leaves for it and its answer treated like any outside data; prompt injection and the answers' quality are in 08 AI design, where the prompts are written.
- **The user decides** the bar (step 2), every accepted risk and every protection that costs (step 4), the numbers with a real choice (step 5), Row-Level Security (step 6), the outside test before launch (step 12) and every ADR (step 13). You give the options and a recommendation; they choose. One decision at a time.
- **A number about the documents is counted by a script before it's written** (the endpoints, the ways in, the threats, the secrets, the accounts, the protections with their check, the list's answers), and the script is run again at the check. A count is never typed from memory: one with no script yet gets one first.
- **Check every claim at its source page, with the date,** not from memory: OWASP (ASVS, the Top 10 lists, the Cheat Sheets), NIST SP 800-63B, the framework's security docs, the browsers' support, the tools' versions and licences, each provider's own page on its second factor and its keys. A quote word for word, the version, and the day it was read ("checked 2026-11-09"). **A standard's edition is read at OWASP's own repository** (the release's tag, such as `v5.0.0_release`), not a summary or a mirror: the requirement ids and their levels change between versions. Security moves fast and memory drifts: a tool can itself be compromised (Trivy, March 2026), a default can change (pnpm 11 waits a day before a new version), a service can move and drop a test (Mozilla's HTTP Observatory moved to MDN in 2024 and no longer tests TLS), and a figure "corrected" from memory can be right after all, so it's cited from the report itself.
- **The map as a data flow diagram with trust boundaries** (the threat-modeling notation: external entities, processes, data stores, numbered data flows, each boundary a dashed box), written as PlantUML (`diagrams/map.puml` next to its `.svg`), drawn at step 3, with a title and a legend. `docs/02-design/diagrams.sh` (set up by `/docs-setup`) draws every diagram of the design from text, in a standard notation (decided 2026-10-20), so they read the same at any company; never a hand-made SVG, a home style, or a script that draws SVG itself. Every flow in the table is on the map with the same number and the same ends. Open it before committing.
- **A number or a rule decided earlier changes everywhere at once** (decided 2026-10-21, after a whole-design check found ~160 stale mentions left behind by later steps): before committing, `grep` all of `docs/` for the old value and its wording (the number, the name, the phrase) and fix every place in the same commit, or say why one stays (a journal line keeps what was true that day; a past count kept on purpose goes into `docs/02-design/checks/facts-history.txt`). `diagrams.sh` runs `checks/facts.py`, which counts the main facts from their sources (tables, addresses, threats, secrets, screens, ADRs, alerts) and stops on a document that states another number; a new fact that many files repeat gets a line in it. **It reads this step's tables by their header lines,** so keep them as the templates below write them: the `| T-nn |` rows of the threats, the map's `| # | From`, the inventory's `| Secret | Opens`, the detection's `| Event | Logged | Alert when` (an alert counted where its threshold is in bold). The `facts.py` that `/docs-setup` writes guards these, and also the ways in that aren't addresses (`| Way in |`), the accounts that reach production (`| Account | Opens`), the protections with their check (`| Protection | Check |`) and the list's answers (the `Applies` column of `asvs-l2.md`: yes, deviation, gap); **add a line for each other count this step repeats.** **Every change to a threat, a protection or a count goes into its file, its row in 11-checks, the README and every document that repeats it, in one commit.**
- **What isn't here:** the legal texts and telling the authority and the people about a breach (02 Compliance; here the technical side of the plan); the AI's prompts and answers' quality (08 AI design); the protections' code (Build, per slice); uptime monitoring and the backups' schedule (01 System design; here only what concerns an attack: their encryption, who restores them, how each copy is proven); the pentest itself (before launch, if chosen).

## Threat modeling
Use this at steps 3 and 4. **The four questions** (Adam Shostack; the Threat Modeling Manifesto, 2020): what are we working on? (the map) what can go wrong? (the threats) what are we going to do about it? (the protections, or the risk accepted) did we do a good enough job? (the checks). An hour at a whiteboard with the team is already a model.

**STRIDE** (Loren Kohnfelder and Praerit Garg, Microsoft, 1999), so no category is forgotten at "what can go wrong?":

| Letter | The threat | Violates | Example | The usual protection |
|---|---|---|---|---|
| **S**poofing | I pretend to be someone else | authenticity | a bot logs in with a password leaked from another site | leaked-password check, limits on login, a second factor |
| **T**ampering | I change data I may not change | integrity | a forged payment webhook marks an account paid | the webhook's signature checked |
| **R**epudiation | I deny doing something, and nothing proves otherwise | non-repudiation | nobody knows who approved a wrong value in shared data | an audit log of the admin's actions |
| **I**nformation disclosure | I see what I may not see | confidentiality | one user reads another's weight; a leaked backup | "is it yours?" on every request; encryption |
| **D**enial of service | I stop the app or make it too expensive | availability | a script asks for 300 password resets and uses up the day's emails on a free plan; someone spends the month's AI budget | limits per endpoint, per account, per IP |
| **E**levation of privilege | I get rights I don't have | authorization | a user sends `"isAdmin": true` in a body and becomes admin | DTOs without that field; the role read only from the database |

**How it's applied:** on every flow of the map (phone → API, API → database, payment provider → API), ask the six letters in turn. What 01–06 already decided goes in as the protection, with its link; what's missing becomes a new protection or an accepted risk, written with its reason.

| Method | Worth it when |
|---|---|
| STRIDE | almost always: the most used, easy to learn |
| LINDDUN (KU Leuven): linking, identifying, detecting, non-compliance and other privacy threats | products with a lot of personal data; a DPIA often covers it |
| PASTA: seven stages from business goals to attack simulation | large companies with a security team and formal risk analysis |
| Attack trees (Bruce Schneier, 1999): the attacker's goal at the top, every path to it below | one goal that matters a lot ("become admin") |
| Tools: OWASP Threat Dragon, Microsoft Threat Modeling Tool, IriusRisk | the team already uses one |

**A risk has four answers:** reduce it (a protection), accept it (written, with why and who accepted it), transfer it (to a provider: the payment provider holds the card data), avoid it (drop the feature).

## The standards
Use this at steps 2 and 12. They're often confused, above all the Top 10 with ASVS.

| Standard | What it is | What it's for |
|---|---|---|
| OWASP Top 10 (2025) | the ten most frequent risk categories in web apps; OWASP calls it "a standard awareness document" | awareness, training, a list so nothing is forgotten |
| OWASP API Security Top 10 (2023, still the latest) | the same for APIs; first, someone else's object asked for by its id (BOLA) | the review of every endpoint |
| OWASP ASVS (5.0.0, May 2025) | 345 verifiable requirements in 17 chapters, on three levels | the security "done when", requirements in a contract, a pentest's checklist |
| NIST SP 800-63B, revision 4 (July 2025) | the US government's authentication rules, followed by the industry | the numbers for passwords, sessions and second factors |
| OWASP Cheat Sheets | short recipes per topic | implementing a protection correctly |
| CWE Top 25 (2025: XSS, SQL injection and CSRF first) | the most dangerous weaknesses in code, from real vulnerability data | code analysis tools report in CWE |
| NIST SSDF, OWASP SAMM | how mature a team's security process is | a CTO decides where to invest |
| ISO/IEC 27001, SOC 2 | a company certified by an auditor | B2B customers ask before they sign |
| OWASP Top 10 for LLM Applications (2026) | the risks of apps with language models, prompt injection first | 08 AI design |

**What changed in the Top 10 in 2025:** broken access control stays first; using components with known vulnerabilities, on the list since 2013, widens into software supply chain failures and rises to third; mishandling of exceptional conditions enters at tenth; logging becomes "logging and alerting".

**ASVS levels** (counted in version 5.0.0's tables): **L1**, 70 requirements, the minimum, the first layer; **L2**, 183 more (253 in all), the level ASVS says "most applications should be striving to achieve"; **L3**, 92 more, for applications that must show the highest level (its example: online banking). Version 4 tied L2 to sensitive data; 5.0 leaves the choice to each product's risk (a startup with little sensitive data may start at L1). Cite a requirement with its version (`v5.0.0-7.5.1`): the numbers change between versions. **What L2 costs beyond writing, to say before the level is chosen:** a second factor for every user (`6.3.3` asks multi-factor authentication, or a combination of single-factor methods, to get into the application; the chapter's introduction: "L2 applications must force the use of multi-factor authentication", calling it "a relatively aggressive stance on MFA", relaxed only with "a clear plan on how the risks around authentication will be mitigated"), a secrets manager such as a key vault (`13.3.1`), TLS between internal services (`12.3.3`), and 128-bit session ids (`7.2.3`); each is met or written as a deviation with its reason. **Quote a requirement from its own row, not from its chapter's introduction:** the two can differ, as they do here.

## Authentication in numbers
Use this at step 5. In short: a password must be long, not complicated; the leaked-password list matters more than any rule; the server slows attempts down, it doesn't lock the account.

| What | The standard says |
|---|---|
| Minimum length | **15** when the password is the only factor, **8** only with a second factor (NIST 800-63B-4, 3.1.1.2, "SHALL"; OWASP the same) |
| Maximum length | at least 64 (NIST, "SHOULD"), so a passphrase fits |
| Composition rules | forbidden ("SHALL NOT"): they produce "Password1!" |
| Periodic change | forbidden; required only on evidence of compromise |
| Leaked and common passwords | checked, the whole password ("SHALL"), and the person told why it was refused |
| Failed attempts | at most **100** consecutive on one account (NIST, 3.2.2); growing waits, "30 seconds up to an hour"; work out when the 100th comes from the waits you choose |
| Password managers and paste | autofill allowed ("SHALL"), paste allowed ("SHOULD") |
| Hints and security questions | forbidden |
| The hash | **Argon2id**, at least 19 MiB of memory, 2 passes, 1 thread (OWASP Password Storage); bcrypt only for legacy systems, and it cuts the password at 72 bytes. **Spring Security's Argon2 defaults are 16 MiB with 2 passes, under OWASP's minimum: set the parameters explicitly** |
| A reset link | single use, expiring "after an appropriate period" (OWASP, no number); NIST: a recovery code sent by email lasts at most 24 hours |

- **Where it usually breaks:** around the hash, not in it. **Credential stuffing:** bots don't guess, they replay passwords leaked elsewhere, so the leaked-password check and the login limit matter more than the algorithm. **Enumeration:** login, sign-up and "forgot password" answer the same whether the address has an account (OWASP's wording: "If that email address is in our database, we will send you an email"). **The reset:** the token is random, stored only as a hash, works once and briefly, and the other sessions end after the change.
- **Leaked passwords, two ways.** A: Have I Been Pwned's range API gets only the first 5 characters of the password's SHA-1 and returns every hash starting with them; the match happens on the server, so the password never leaves (k-anonymity); free, no key, no rate limit, behind Cloudflare; with `Add-Padding` every answer has 800–1,000 rows, so its size tells nothing, and the padding's rows carry a count of 0 and are dropped before the match. B: a local list, downloaded and kept up to date. Spring Security has A built in since 6.3 (`HaveIBeenPwnedRestApiPasswordChecker`), with two details found in its source (October 2026): it **fails open** (if the service doesn't answer, the password passes) and sends no padding; it checks at login on its own, but sign-up and password change must call it.
- **Two clocks on a session:** inactivity and total. **NIST ties them to the assurance level:** at AAL1 (a password alone) the total "should" be at most 30 days and inactivity isn't required; at AAL2 (a second factor) at most 24 hours in total and 1 hour inactive; at AAL3, 12 hours and 15 minutes. **OWASP:** 2–5 minutes inactive for high-value apps, 15–30 for low-risk ones, an absolute timeout always, a new session id after login. **Spring Boot's default is 30 minutes inactive** (`server.servlet.session.timeout`), too short for an app opened a few times a day; Spring Session's remember-me keeps a session 30 days by default, **but its cookie serializer then writes `Max-Age` as `Integer.MAX_VALUE`**, relying on the session's end, so the cookie stays in the browser for decades: a small `CookieSerializer` of your own writes what's left of the total instead.
- **The session id's entropy:** ASVS asks at least 128 random bits (`7.2.3`); Spring Session's default id is a UUID, 122 random bits: a `SessionIdGenerator` of 27 bytes from `SecureRandom` in base64url gives 36 characters and fits its `char(36)` column. **A person's list of devices** (`7.5.2`, L2): see them, sign out one or all the others; **a remote sign-out doesn't wipe an offline app's data** on that device: say so on the screen.
- **Step-up ("confirm it's you")** before changing the email or the password and before deleting the account: someone holding an unlocked phone can't lock the owner out. NIST gives no number; GitHub's sudo mode lasts **2 hours**, each sensitive action restarting the clock; ASVS 5.0 asks full reauthentication before changing the email (7.5.1); Spring Security 7 has it built in (a recent factor: its docs' examples, 30 minutes for an admin area, 1 hour for settings). A step-up gives a new session id, as a login does. **For an account made with Google only, Google can't be made to ask the password again:** its `prompt` takes `none`, `consent`, `select_account`; ask `auth_time`, use the account chooser, and let a passkey confirm instead; say what remains.
- **A second factor and passkeys.** A TOTP code stops a bot holding only the password, not a fake site that also asks for the code; a passkey stops the fake site too, because it's bound to the site's address. FIDO Alliance estimates 7 billion passkeys in use (October 2026); WebAuthn Level 3 is a W3C Recommendation since 25 August 2026; Spring Security supports passkeys since 6.4. NIST calls synced passkeys "syncable authenticators" and accepts them up to AAL2. The real question is **for whom**: an admin who changes shared data for everyone is a different risk from a user. **A passkey is added only with a passkey,** confirmed minutes ago, never with "confirm it's you" by password: otherwise a stolen password adds its own passkey and the second factor protects nothing; the first one through a bounded window (24 hours after the role is given) or a procedure on the server.
- **Limits: slow down, don't lock.** An account locked after 5 wrong passwords can be locked by anyone who knows the email. Count on several keys at once (per IP, per account, per target email), answer 429 with `Retry-After`. OWASP counts per account, not only per IP, because bots rotate IPs. **Spring has no built-in limits** (the request has been open since 2016): a library (Bucket4j, with a PostgreSQL back-end) or the proxy. **NIST's 100 failures in a row is itself a stop** anyone who knows the email can reach: written as an accepted risk, with a reset that reopens it, the owner told, and the state kept in a column (a token bucket can't count "in a row"). **Let the waits follow the failures in a row, and work out the arithmetic before writing a number:** 10 failures at once, then waits of 1, 5 and 15 minutes, then one an hour, give a bot 36 guesses the first day and 24 a day after, and the 100th failure comes 21 + 87 × 60 = 5,241 minutes after the first, about 3.6 days, not the "about a day" the first run wrote. The count goes back to 0 at a successful login, a reset, or a day without a failure. **The IP the limits count comes from the proxy:** the proxy overwrites `X-Forwarded-For`, and the app trusts it only from the proxy, or a forged header gets past every per-IP limit.
- **Sign-in with Google:** link to an existing account only by the identity provider's `sub`, and only when the email is trusted; an unconfirmed account loses its password at the link. Otherwise someone who signed up first with your address and a password they know gets in after you: "pre-account hijacking" (Sudhodanan and Paverd, USENIX Security 2022: at least 35 of 75 popular services were vulnerable). **Google says its email claim is authoritative only for `@gmail.com` addresses and Workspace ones (with `hd`)**; for others, even with `email_verified`, it recommends a further check, because the address may have changed hands.

## Authorization and the database
Use this at step 6. First in the OWASP API Security Top 10 is someone else's object asked for by its id (BOLA): the server checks "logged in?" and not "is it yours?". The layers:
1. every query filters by the owner (the person, the team, the tenant), never a row loaded by its id alone; **a list or a search, with no id to swap, is tested on two persons' data** and must return only one's, whatever builds its query;
2. someone else's item answers 404, not 403, so ids can't be probed; 403 where the address is known and only the role is missing (a user on an admin address, a member on the owner's); decided once for the product, in the conventions;
3. every endpoint is closed unless it states who may call it (in Spring, `anyRequest().denyAll()` last), and a test fails on one without a rule; **a script compares `openapi.yaml` with the rules** and writes the "is it yours?" test of every address with an id, so a new one can't be forgotten;
4. optionally, the database itself:

| | Filters in the code | Plus Row-Level Security in PostgreSQL |
|---|---|---|
| What it does | the owner's id in every query, checked by an architecture rule and a per-endpoint test | the database adds the condition to every query, from a user id set at the start of each transaction |
| What it catches besides | — | a hand-written query (reports, raw SQL) that forgot the filter |
| What it costs | nothing more | a policy per table; the id set per transaction (`set_config('app.user_id', …, true)`) so it doesn't stay on a pooled connection; the policy's columns indexed; **the table's owner bypasses it** unless `FORCE ROW LEVEL SECURITY`; superusers and `BYPASSRLS` roles always do. A policy that reads only the row's own columns is the fastest case. **The jobs that read across people and the backup need a way past it:** `pg_dump` turns row security off and stops with an error when its user can't bypass it, and on a managed database a `BYPASSRLS` role may not be creatable (on OVHcloud, `avnadmin` hasn't it, so it can't give it), so a fourth database user with policies of its own |
| Who uses it | the usual way with an ORM (Spring Data, Rails, Django) | Supabase (it asks for it on every table in an exposed schema), multi-tenant products with strict requirements |

**The database's users:** the app never connects as the tables' owner. One user runs the migrations (creates and changes tables), the app's user reads and writes rows, nothing more, a backup's user only reads (`SELECT` for `pg_dump`): an SQL injection can't drop a table, and the owner's bypass of Row-Level Security doesn't apply to the app. **The owner's default privileges** grant every new table to the app's user (and, for reading, the backup's), set with the users before the first migration and global (no `IN SCHEMA`), with `USAGE` on the schemas the migrations create, or a module's new schema is out of reach. A CI test tries `DROP TABLE` and `TRUNCATE` as the app's user and expects them to fail, and any write as the backup's. **An emergency command run by hand** (everyone signed out, a lost admin's passkey removed) runs as the owner, from a reviewed SQL file, never typed into a console, and writes its line in the audit log. On a managed database, check what the given account may do (on OVHcloud, `avnadmin` isn't a superuser but can create roles, and OVHcloud advises against using it for the app). Since PostgreSQL 15, only the database's owner may create in `public` without an explicit grant, in databases created since.

**Mass assignment:** bind only the fields a request may set, through DTOs that leave out the sensitive ones (the role, the owner, the price) (OWASP Mass Assignment Cheat Sheet). **An audit log the app writes is granted `INSERT` and `SELECT` only** to the app's user, its cleanup run by the owner: otherwise the account it audits can rewrite it (`16.4.2`).

## The browser
Use this at step 7. React already stops most XSS; the headers are the safety net for the day someone writes `dangerouslySetInnerHTML`. **A reverse proxy usually sets no security header on its own** (Caddy doesn't): they're written in its configuration. The framework may write a few on its own answers (Spring Security: `X-Content-Type-Options`, `X-Frame-Options`, `X-XSS-Protection: 0`, the cache headers, and HSTS only on a request it sees as HTTPS, which an API behind a proxy talking plain HTTP doesn't see): say which layer writes each header. **Draw the origins first** (the app, the API, the static site, the payment and login providers: one origin or several, sharing a registrable domain or not): CORS, `SameSite`'s reach and which scripts and frames are foreign follow from that drawing.

| Header | What it does | Value (OWASP) |
|---|---|---|
| `Content-Security-Policy` | where the page may load scripts, styles, images and connections from; stops an XSS even when the attacker's text reached the page | ASVS `3.4.3` asks `object-src 'none'`, `base-uri 'none'` and an allowlist, nonces or hashes: an SPA that its bundler builds into external files (Vite does) needs only `script-src 'self'` and the hosts it really loads, hashes (web.dev's "strict CSP") only for an inline script; plus `frame-ancestors 'none'`, `form-action 'self'`, `require-trusted-types-for 'script'`; never `'unsafe-inline'` for scripts |
| `Strict-Transport-Security` | the browser refuses HTTP on the domain from now on | `max-age=63072000; includeSubDomains` (2 years); `preload` only knowingly: leaving the browsers' list takes months |
| `X-Content-Type-Options` | the browser doesn't guess a file's type (a "photo" that is HTML) | `nosniff` |
| `Referrer-Policy` | how much of the address leaves for another site | `strict-origin-when-cross-origin` (the Cheat Sheet) or `no-referrer` (the Secure Headers Project); `no-referrer` on a page with a token in its address |
| `Permissions-Policy` | which browser features the page may use | off for what's unused; **keep what the product needs** (`camera=(self)` for an app that scans); only Chromium applies it, Firefox and Safari ignore it |
| `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy` | isolate the window and the resources from other sites | `same-origin`; resources `same-origin` or `same-site` (the two OWASP sources differ); tried with the payment window and the identity provider |
| `X-Frame-Options` | no one frames the app to trick a click (clickjacking) | `DENY`, and `frame-ancestors 'none'` in the CSP |
| `Clear-Site-Data` | at sign-out, the browser clears its cache, cookies and storage | `"cache", "cookies", "storage"`, on the sign-out's answer; a net under the app's own wipe, since Safari doesn't support `"cache"` |

- **Not set any more:** `X-XSS-Protection` (off or absent; the CSP replaces it), `Expect-CT`, `Feature-Policy` (now `Permissions-Policy`); remove `X-Powered-By`.
- **Trusted Types**, in every major browser since February 2026 (Chrome 83, Firefox 148, Safari 26): with `require-trusted-types-for 'script'` in the CSP, `innerHTML` with a plain string stops working, only through a policy you write; the net under `dangerouslySetInnerHTML`. **A script's address from a string is refused too:** registering the service worker (`navigator.serviceWorker.register('/sw.js')`, as vite-plugin-pwa does), `new Worker(…)`, a payment provider's loader that adds a `<script>` and sets its address. Without a policy the app loses its offline mode and its checkout; one `default` policy that names exactly those addresses, tried in a real browser.
- **CSRF with a session cookie.** The cookie goes with every request to the domain, even one started by another site. `SameSite=Lax` stops most cases, but OWASP and Spring treat it as defence in depth, not the whole defence; **only Chrome and Edge default to `Lax`**, Firefox and Safari don't, so set it explicitly. Spring Security 7 (November 2025) has `csrf.spa()`: the token in a cookie the app reads and sends back in a header another site can't set. The newer way, `Sec-Fetch-Site` set by the browser (Go's `CrossOriginProtection` since August 2025; OWASP accepts it with an `Origin` check when it's missing), isn't in Spring yet.
- **Cookies:** `Secure`, `HttpOnly`, `SameSite` explicit, no `Domain`, and the `__Host-` prefix, which forces those (OWASP recommends it for session ids). **Behind a proxy that talks plain HTTP to the app, set `Secure` explicitly:** Spring sets it only when the request it sees is HTTPS, and a browser refuses a `__Host-` cookie without it, so nobody could log in. The CSRF cookie gets its attributes too (not `HttpOnly`, since the app reads it). Check each cookie behind the proxy, and that the login provider's return still carries the session.
- **`Cache-Control: no-store`** on answers with sensitive data: the browser keeps none on disk after sign-out. OWASP asks it on every API answer a browser reads; web.dev warns against it on pages, since they lose the back/forward cache. For sensitive API answers OWASP wins; name the exceptions (a public file the same for everyone, a photo that never changes). It doesn't break `ETag`: an app that keeps its own copies (IndexedDB) sends `If-None-Match` itself and gets 304.
- **CORS:** same origin behind the proxy, so none; a list of exact origins otherwise, never `*` with credentials.
- **Other origins of our own:** a landing page with an analytics script, a static site with the legal pages, live on **another host** than the app (`3.5.4`): on the same origin their scripts could read the app's IndexedDB. **A payment provider's script** (Paddle.js, Stripe.js) runs on our origin: load it only on the paying screen, check whether the provider offers a hosted page instead (Paddle's is for approved mobile apps only, October 2026), and try its CSP hosts in report-only mode, since providers rarely publish them.

## Data, files and secrets
Use this at step 8.
- **The inventory of secrets**, one row each: what it opens, where it lives, who can read it, how it's rotated, what to do if it leaks. "Secrets only on the server" is the start, not the inventory. A key that must never be lost (a key that links proofs kept for years) is kept outside the server too, and never rotated without keeping the old one.
- **Where secrets live, simple to complex:** a file on the server readable only by the app's user; encrypted files in the repository (SOPS, a CNCF project, with age); a secret manager (HashiCorp Vault, OpenBao, its open-source fork, or the cloud's own: OVHcloud Secret Manager, generally available since June 2025, Scaleway Secret Manager), with logged access and rotation. The last two earn their place with several people or servers; with one server and one person, a strict file plus an encrypted copy elsewhere is usually enough, unless the bar asks a vault (ASVS L2's `13.3.1`). **Every way keeps one secret on the server** (the "secret zero" that opens the rest): narrow it to one identity per process, each with read rights on its own path only.
- **Each provider's key shrunk:** the fewest rights the provider allows, by the provider's own names; an expiry where it offers one; an IP restriction; a spend cap on anything paid per call. Where a provider offers only long-lived keys, that's a deviation from ASVS `13.2.1`, written with what stands in its place.
- **Encryption in layers,** each against a different attacker: in transit (HTTPS to the proxy, TLS to the database); at rest by the provider (against a disk stolen from the data centre, not against someone coming in through the app); per column or in the app (against a stolen backup too, but search and sort get harder). The question is "against whom", not "encrypt or not"; never only "encrypted: yes". **Decide the columns last,** once you know which ways to the database are already closed, and say a no out loud, with when you'd revisit.
- **The levels of the data** (ASVS `14.1.2`): four or five (health or financial, personal, internal or shared, public, secrets), taken from the record of processing, each with its rules for who sees it, caching, logs, export, deletion and the backups.
- **A backup is proven twice:** every copy tested by the job that makes it, before it leaves (a throwaway restore, the rows counted against the live database, the file's SHA-256 sent with the upload and checked by the storage, so a write-only key is enough), and a restore drill on a calendar (before the beta, then every 6 months) that uses the offline key, the script and the real copy. Each copy a row: who makes it, where it goes, how long it's kept, who encrypts it and where that key lives, who restores and how.
- **Uploaded files** (OWASP File Upload Cheat Sheet): an allowlist of types, checked by content, with the file's signature as one check but never the only one; a size limit; an image decoded and re-encoded on the server, which also drops its metadata (a phone photo can carry the GPS position of a kitchen, so a home address); a new name; private storage served through links that expire. **Files we import ourselves count too:** an XML file is parsed with DTDs and external entities off (XXE), a zip is unpacked with limits on its size and its number of files.
- **Logs never hold** passwords, tokens, cookies, session ids (a hash at most), keys, connection strings, request bodies with sensitive data, or what the person asked not to keep (OWASP Logging Cheat Sheet); the route as a template, not the raw path with ids. **The proxy's access log writes the page's address too:** a token from an emailed link (`/reset-password?token=…`) lands there unless its log filter removes it.
- **Outside services' answers are outside data:** validated like a user's input, and a URL is never fetched from what a user sent without an allowlist (SSRF: OWASP's cheat sheet).

## The supply chain
Use this at step 9. A `pnpm install` runs code written by hundreds of people on the laptop and in CI, where the keys are.

| When | What | How | What would have stopped it |
|---|---|---|---|
| March 2024 | XZ Utils (CVE-2024-3094) | years of trust earned by a "contributor", then a backdoor in the published archives | nothing simple: an engineer noticed SSH logins about half a second slower, before most distributions' stable releases |
| March 2025 | `tj-actions/changed-files` (CVE-2025-30066) | the action's tags moved to a commit that printed CI secrets to the log | actions pinned to a commit (SHA), not a tag |
| September 2025 | `chalk` and `debug` on npm | a maintainer phished; new versions that stole crypto from browsers | a wait before any new version |
| September and November 2025 | Shai-Hulud, an npm worm | stole the installing machine's tokens and published itself into the victim's packages; 500+ packages removed | install scripts off; short-lived publishing tokens |
| March 2026 | Trivy (CVE-2026-33634), **a vulnerability scanner** | a bad release, and 76 of 77 tags of its GitHub Action moved to bad code | security tools are dependencies too: pinned by SHA |
| May 2026 | TanStack: 84 bad versions in 42 packages, `@tanstack/react-router` among them | a `pull_request_target` workflow, a poisoned CI cache, then the publishing token taken from the runner's memory; each bad version lived about 2 h 53 min to 4 h 35 min, the whole attack 4 h 35 min; the payload came through an `optionalDependencies` entry pointing at a `github:` commit | a one-day wait: never installed |

**What protects, cheap to expensive:** the lockfile committed and CI installing only from it; **a wait before any new version** (pnpm 11 waits a day by default, `minimumReleaseAge`, for indirect dependencies too; write it anyway, since only an explicit value makes `minimumReleaseAgeStrict` true, so the install fails instead of falling back to a younger version); a longer wait before the update bot proposes an update (Renovate's `minimumReleaseAge`: 3 days on the first run, an `[ASSUMPTION]` past the hours the known bad versions lived, for every ecosystem, Maven included, which has no wait of its own); **install scripts off** (pnpm since 10, npm since 12; only packages listed in `allowBuilds` run code at install), and an indirect dependency never from git or a tarball's URL (pnpm's `blockExoticSubdeps`, TanStack's way in); frequent updates, read (Renovate or Dependabot, a security fix as its own PR at once, still after a day, since a "fix" can be the attack too: Renovate's own default for a vulnerability's PR is no wait at all; for one already in CISA's KEV the wait is skipped by hand, the reason written in the PR; Dependabot alerts are free on every plan); a dependency scanner in CI failing on a critical vulnerability; **CI kept tight:** actions pinned by SHA and images by digest, the update bot moving the pins, `GITHUB_TOKEN` read-only by default and raised per job, no `pull_request_target` (where Trivy's and TanStack's compromises started), no `${{ github.event.… }}` written inside a `run:` script (a branch's name or a PR's title would become shell code; through `env:` instead), a check on the workflows in CI (zizmor), GitHub's workflow lockfiles (public preview); **an SBOM** (`pnpm sbom`, the CycloneDX Maven plugin), so on the next incident you know in minutes whether you're affected (it lists the libraries, not the base image's system packages: the weekly scan of the images answers those); **what an AI coding agent may run** and which secrets it never sees. At work, further: OpenSSF Scorecard (20 automatic checks of an open-source project, before choosing a library) and SLSA 1.2 (builds anyone can verify).
**Check the code host's plan before counting on it.** On GitHub's free plan a private repository has no protected `main` and no environment secrets ("If you are using GitHub Free, environment secrets are only available in public repositories"), so any branch's workflow can read the deploy's secrets: deny an AI agent the workflow files, run the deploy job only on a push to `main` (`github.event_name == 'push'` too, since the ref alone lets a manual or scheduled run through), give each deploy key only its own server, or pay for the plan that has them. **The scanners cost CI minutes:** add them to the minutes' table and run the heavy ones only when the dependencies or the code they read changed. **Invented example tokens** in the documents trip the secret scanner once copied into the code: a `.gitleaksignore` with the reason, or values that look fake. **A planted mistake must sit where the real one would:** pnpm 11 and later may write `pnpm-lock.yaml` as two YAML documents, and a scanner reading only the first reports no dependencies, without an error; plant the vulnerable version in a lockfile written by the stack's own pnpm, and fail CI when the scanner lists no package from the real lockfile.
**An AI coding agent is a new insider:** no production secret where it runs; `ssh`, `scp`, `sftp` and `rsync` denied, the SSH keys unreadable, the workflows unwritable; never a push to `main`; no MCP server or plugin in the project's settings unless the owner adds it after reading it like a dependency (they run outside the agent's sandbox, with the owner's rights); its own updates from a stable channel, the same idea as the wait; its code through the same scanners and review. **Write which of these the tool enforces and which only ask it:** Claude Code's deny rules match the command as the agent writes it (`/usr/bin/ssh` or `sh -c 'ssh …'` passes a `Bash(ssh *)` rule), so its sandbox is on too, enforced by the operating system on every command and what it starts, with the keys of paid services denied as variables; a command excluded from the sandbox is written as the known gap. What the agent reads (a package's files, a web page, an issue) may carry instructions: the rules hold whatever it reads.

## The server and the accounts
Use this at step 10. On one server the protections are few and known: a supported operating system with its end date written; SSH with keys only, no password and no root login, only the users that need it, a deploy key that can run only the deploy script (`restrict,command="…"` in `authorized_keys`); a firewall letting through only 80, 443 and SSH, and 443 over UDP if the proxy serves HTTP/3 (Caddy does by default); the system's security updates installed automatically, with who reboots after a kernel update, when, in which time zone; a database reachable only from the server's IP, connected with the certificate checked (`sslmode=verify-full`, not the `require` a provider's connection string often gives, which "would accept a certificate presented by anyone"); the provider's DDoS protection (OVHcloud includes it on its VPSs, except Local Zone ones); TLS 1.2 and 1.3 (Mozilla's "intermediate" profile; Caddy's default), HTTP redirected to HTTPS, certificates renewed automatically as their lifetimes shrink (Let's Encrypt: 64 days from February 2027, 45 from February 2028), with an alert for one about to expire; a CAA record naming the one certificate authority allowed, and that one named in the proxy too (Caddy falls back to ZeroSSL by default, which the record would refuse). **Only the proxy publishes ports, checked from outside:** a port Docker publishes skips `ufw` ("traffic to and from that container gets diverted before it goes through the ufw firewall settings"), so the firewall can't close what Docker opens; a CI check on the Compose file. **No fail2ban with keys only:** there's no password to guess, and OpenSSH's own `PerSourcePenalties` (on by default since 9.8) slows an address that keeps failing. Every link left in plain text (the proxy to the app on one server) is a deviation with its reason and the event that reopens it.

**The providers' accounts matter as much as the server:** the code host, the hosting provider, the cloud with the AI key, the payment provider, the email provider, the log service, the domain registrar, the password manager and the owner's own mailbox (it resets every other password), each with a second factor (a passkey or a hardware key where offered, else an app's code, never SMS) and recovery codes kept offline. **Check what each provider offers on its own page,** with the date: one may offer no passkey, another none at all; an account that offers no second factor is an exception, accepted in writing with what reduces it. Verizon DBIR 2026 (22,000+ confirmed breaches): stolen credentials are the commonest action, used in 36%, but as the first way in exploited vulnerabilities passed them for the first time (31% against 13%); a third party is involved in 48%.

## Detection and response
Use this at step 11.
- **Security events logged, taken from the threat model, not from a library's defaults:** every login (failed or not, with its method), and successful ones from a new device; limits hit; password and email changes; roles given and taken; every admin action; every control that failed or was bypassed (a CSRF token missing, a webhook's signature wrong, a CSP violation, the leaked-password service unreachable); unusual numbers of 403 and 404; the server's own SSH logins. Each with when, where, who, what, and never the forbidden fields; **an integration test on every PR** causes each event once and checks its line. **Alerts on patterns, not on every event** (hundreds of failed logins a minute; a new admin): an alert for everything gets read by nobody (OWASP's "alarm fog"); each threshold an `[ASSUMPTION]`, each alert fired once on purpose before the beta.
- **The inventory of logs** (ASVS `16.1.1`): each log the product has (the app's, the proxy's, the server's journal, the database's audit, each provider's), its format, where it's shipped, who reads it, how long it's kept, what it costs. **Ship the server's journal off the server** (Vector's `journald` source, say), so a taken server can't erase its SSH logins. Every time in UTC, and the server's clock synchronised (chrony, with Network Time Security on; ASVS `16.2.2`).
- **The technical side of the breach plan, the first hour in order:** the evidence kept first, before any rotation or restart could erase it, each file's SHA-256 written with who took it and when (the chain of custody); then the leaked key rotated as its inventory row says, everyone signed out (deleting the session rows), the affected part taken offline; each step with its exact command or console page and who runs it. The legal side stays in compliance.
- **How fast a vulnerability is fixed,** from three public signals: CVSS 4.0 (November 2023) for technical severity, 0–10; EPSS (FIRST, version 5, June 2026) for the probability of exploitation in the next 30 days, recalculated daily; CISA's KEV catalog for those already exploited (1,746 on 16 October 2026). One in KEV is fixed first, whatever its score. **Argue each time frame against a published one:** CISA's BOD 26-04 (10 June 2026, revoking BOD 22-01) gives US federal agencies 3 days for a KEV entry that is also at least two of publicly exposed, automatable and of total control, 14 days for a KEV entry with one or none, 60 days for some outside KEV; PCI DSS 4.0.1 (6.3.3) a month for a critical one (read through secondary copies: the standard sits behind PCI SSC's licence page). **The clock starts** when a scanner, an advisory or a report makes the vulnerability known to you, or at its KEV entry, whichever comes first, as BOD 26-04 counts. Verizon DBIR 2026: only 26% of KEV vulnerabilities were fully fixed, after a median of 43 days.
- **How a report reaches you:** `/.well-known/security.txt` (RFC 9116, April 2022) with `Contact` and `Expires` (under a year ahead, which the RFC recommends; CI fails when its end is near), **on every host name you serve**, since a file "MUST only apply to the domain or IP address in the URI used to retrieve it"; then a vulnerability disclosure policy (what good-faith researchers may test, no payment), a bug bounty (rewards; European platforms: YesWeHack, Intigriti), a pentest (a paid specialist, a few days, a report).

## The law
Use this at steps 2 and 11. **GDPR article 32** asks measures "appropriate to the risk", given the state of the art and the cost, and names four: pseudonymisation and encryption; confidentiality, integrity, availability and resilience; restoring data in time after an incident; **regular testing of the measures**. Breaking it: up to €10 million or 2% of turnover (article 83(4)). **The Cyber Resilience Act** (Regulation (EU) 2024/2847) asks security of products with digital elements sold in the EU: reporting exploited vulnerabilities from 11 September 2026, the rest from 11 December 2027; **a web app used only in a browser, a PWA included, isn't such a product** (the Commission's guidance, 27 July 2026), while a native or store-wrapped app would bring its backend in as remote data processing. **NIS2** (Directive (EU) 2022/2555; in Romania, OUG 155/2024) applies, as a rule, to medium and large companies (50+ people, or turnover and balance sheet both over €10 million). ENISA published a Secure by Design and Default Playbook for SMEs (July 2026).

## Steps

### 1. Read what exists
As in "Read first": every document, and **one list of everything 01–06 left for Security**, each with where it came from, **gathered by a script** that greps the earlier folders, the PRD and the ADRs (`checks/left-for-security.sh`), run again at step 14; the list goes into the README's open questions (`Question | Left by | Answered at | When`). If an app exists, read it for facts (the headers it sends, how sessions are kept, who can reach production), written as facts, not as a model. Check the earlier files' security facts at their official sources and write what contradicts or completes them, each with the step that fixes it. List what's missing and ask only that.

### 2. What is protected, and from whom
- **the assets,** most sensitive first, taken from the record of processing and the data model, not from memory, each with what it means to be **seen** by the wrong person, **changed** or **lost** (a dash where a harm doesn't exist), each harm tied to a real consequence (a law's article, a budget used up, someone's history lost): health or personal data, accounts and their sessions, the admin's rights, shared data, the subscription's state, the keys, a paid outside budget (the AI), the copies (exports, backups), the proofs you must keep, the logs, the app being up;
- **the realistic attackers,** most likely first, with what each wants and can do: bots replaying leaked passwords, a curious or malicious user, a member of a shared space, someone holding an unlocked phone, a compromised package or data source, whoever steals the laptop or the code host's account, the owner making a mistake, an AI agent with too many rights; and **who is out of scope** (an attacker with a state's resources; a provider's staff, transferred to its contract), with why, never left out;
- **the bar:** the ASVS level the product aims for, with the argument card (the data, the users, the customers' expectations, the work it means, why not the level above). **The user decides.** **Read the chosen level's requirements one by one before the user answers,** counted by a script from OWASP's release (70 at L1, 183 more at L2), and say upfront the ones that cost more than writing (above), each with the step that decides it: met, or a written deviation.

### 3. The map and its trust boundaries
- **the data flow diagram** with its boundaries (`map.puml`, drawn by `diagrams.sh`): the users' devices, the proxy, the API, the database, files, every provider, the code host and CI, the owner's laptop and accounts; each boundary with one sentence on why it's there;
- **one row per numbered flow** (`| # | From → to | Data that crosses | Guarded by | Open |`): an arrow starts at whoever opens the connection; **every outside party that receives data is a flow, browsers included** (a payment provider's script, a login page, an analytics script on the static site); "Open" names the later step that decides it;
- **the API's ways in, counted by a script** that joins `openapi.yaml` (how a caller proves who it is) with the API map (who may call each address), grouped by who may call, with how many carry an id in the path and how many are limited, failing on any mismatch between the two (`checks/ways-in.sh`); the same script writes the "is it yours?" test of every address with an id (`checks/is-it-yours.md`); the addresses outside the contract by design (the framework's own, a health check) counted and named;
- **the ways in that aren't addresses,** one row each (who can use it, what data passes, what guards it): webhooks, links in emails, uploaded files, the static site and its forms, the outside data you read, the support inbox, the documentation endpoints, SSH, the database, the secrets' store, CI, the dependencies, the providers' consoles, the domain, the owner's mailbox and password manager, staging;
- **"Found while drawing":** every gap the map shows (a flow in plain text, a store reachable from anywhere, a check that collides with a limit), each with the step that closes it. Open the drawing before committing.

### 4. The threats, in chunks
One area per chunk, counted first (on MacroMate: accounts and login; personal data and shared spaces; shared data and the admin; payments; the AI and files; sync and the phone; the server and the supply chain). On every flow of the area that crosses a boundary, the six letters of STRIDE, with the OWASP Top 10 and API Top 10 at hand so no category is forgotten. One row per threat: an id (`T-01`) never reused, the flow's number, the letters, **a scenario an attacker could act on, in one sentence, never a category's name**, how likely and how bad (low, medium, high), **the protection that exists** (linked to 01–06), the gap and the new protection with the step that decides it, **how it's checked** (the row of 11-checks that proves it), and the decision (reduce, accept, transfer, avoid). **An accepted risk is written with its reason, who accepted it and when it's revisited, and goes into the README. The user decides** each accepted risk and each protection that costs; the areas are confirmed one at a time.

### 5. Authentication and sessions, with their numbers
One decision per chunk, in a fixed order, from "Authentication in numbers": the password's minimum and maximum length; the leaked-password check (an outside service or a local list, and what happens when it doesn't answer); the hash's parameters, **measured on the server's number of cores with the library the framework really runs** (OWASP: under a second; `checks/argon2-time.sh`), measured again on the real server before the first user; linking an identity provider; the session's two clocks and remember-me; the step-up's minutes; how long each emailed link lasts; the answers that don't reveal which addresses have an account; a second factor, and for whom; and last **the table of limits,** which needs all the others: every address that costs a hash, an email, an AI call or an outside service, how many attempts, in what window, counted by what (IP, account, target email, the whole app), what the person sees, never a lockout alone. Each number with its card; **read the framework's source where its documentation is vague** (what it does when an outside service doesn't answer, its real defaults); **the user decides** each real choice; **every document the decision touches changes the same day** (the PRD, the API's fields and errors, the contract, the screens' texts, the data model's columns), each with a journal line: a decision left only here is one Build won't see.

### 6. Authorization and the database
The access rule of every endpoint, from the API's map, **checked by a script against `openapi.yaml`** (no endpoint without a rule; deny by default); the test "user A asks for user B's data" on every endpoint with an id, written by the script, someone else's id answered like one that doesn't exist; **the two-persons test** on every list and search without an id; a shared space's own rules (who may delete what) each tested on the addresses they apply to; 404 or 403, decided once; the admin's actions and how the role is given, read from the database at every request, never from the request or a long-lived token, every admin action in an audit log; mass assignment, with a test that sends the forbidden fields and finds nothing changed; **the database's users** (migrations, the app, the backup reading only, read-only for reports if needed), each with its grants and default privileges, and a CI test as the app's user that expects `DROP TABLE` and `TRUNCATE` to fail; the runbook's commands run as the owner; Row-Level Security yes or no, **the user decides**, a written decision with what it would close and cost, what replaces it, and when to revisit; if yes, **tried on a real PostgreSQL** with the app's user and a pooled connection.

### 7. The browser
The origins drawn first; the cookies (name, every attribute with why, checked behind the proxy); the CSRF defence, the addresses it skips (webhooks) and the ones people forget (the login, the logout, the passkeys); **the exact CSP**, directive by directive, **tried on the UI design's pages in a real browser** (served with the header, the violations counted per directive), each planted mistake caught and a clean page doing what the app does passing (`checks/csp-pages.mjs`, `csp.txt`, `csp-planted/`); Trusted Types with its `default` policy; the other headers, each against a reference and the layer that writes it, a difference from OWASP's value argued; which answers get `no-store`, with the exceptions named; CORS; what the service worker caches, as a rule a test checks; every outside script (a payment provider's): where and when it loads, what it could reach on your origin, what reduces it, what's accepted and by whom, its hosts tried first in `Content-Security-Policy-Report-Only`.

### 8. Data, files and secrets
Encryption per layer, each against its attacker (what the provider does, what we do), the columns last; **the levels of the data** with their rules; **each backup as a row, proven twice** (the job's own test, a drill on a calendar); where the secrets live, with the "secret zero" each option leaves; **the inventory of secrets**, never a value; the keys that must never be lost and where their offline copy lives, with the drill that tests it; each provider's key shrunk; uploaded files; what never reaches the logs.

### 9. Dependencies, CI and AI agents
The road the code takes to production (the laptops, the AI agent, the repository, CI, the registries, the servers), with who can change what at each step; how new versions arrive and how long they wait, at install and before an update is proposed; how security fixes arrive (their own PR at once, outside the weekly one) and who may skip the wait; the pins (actions by SHA, images by digest); which scanners run at which CI stage, what fails the build and what only warns, within the CI minutes' budget, an overrun written as an open question; CI's rights; the container images (where from, how updated, non-root, read-only, started by digest); the SBOM; what an AI coding agent may read, run and push, and which of those the tool enforces. **Each scanner tried on its planted mistake and a clean case** (`checks/supply-chain.sh` with `supply-chain/`), its version written.

### 10. The server and the accounts
Every door into the server (each open port, each way an admin gets in: SSH, the provider's console and rescue mode, each container's port), what's closed and how what stays open is locked, **checked from outside**; how the system stays patched and who reboots when; the database reachable only from the server, with the certificate checked; TLS on every link, the CAA record, every link left in plain text as a deviation; what the provider does for you (DDoS, disk encryption), in its own words; **a second factor on every account that reaches production**, the mailbox and the password manager first, each checked on its provider's page, recovery codes offline; who else has access; what happens if the one person who holds the keys can't act: a stand-in, or the risk written.

### 11. Detection and response
The security events logged, from the threats, each tested to leave its line with no forbidden field; the alerts with their thresholds (in the system design's monitoring); the inventory of logs and the clocks; the admin's audit log, only added to and read by the app's user, kept as long as a mistake can take to be found; **the technical side of the breach plan**, the first hour in order, each step with its exact command; **the time to fix** by severity (KEV first), argued against a published one, with when its clock starts; `security.txt` on every host name and how a report reaches the owner.

### 12. How it's checked
Three chunks.
1. **Every protection with its check** (`| Protection | Check | Where | When | Tried on |`): gathered from the threats and the files 04–10, not from memory; **each check's exact input and expected answer** (the status, the error code), so Build can't soften it; each at the cheapest level that can catch the mistake (a small test, an integration test on a real database, end-to-end in a browser, a CI script, the deploy, a scan from outside, a person with a list), with when it runs; **guard tests that walk every endpoint** rather than one test per case, so next month's endpoint is covered; each row names the threats it proves, **every threat that isn't only accepted or transferred is named in a row**, counted by a script; below the table, the accepted and transferred ones, split into those with no check of their own and those whose reducing protection a row above checks; every script and scanner with its "tried on".
2. **The ASVS list of the chosen level**, in its own file (`asvs-l2.md`, named after the level): every requirement **copied from OWASP's release files by a script**, with its id and version, its level and what it asks in one plain sentence, counted against the release (each once, none of the level above; 253 at L2); **drafted by a few agents in parallel** (four on the first run), one per group of chapters, each reading the design and marking every requirement yes, no, deviation or gap with where it's met and the row of 11-checks that checks it; every "no" names the technology that isn't used (no GraphQL, no WebSockets, no tokens we issue), so a later one brings the lines back; **every gap confirmed in the file it names before it's shown**; then a script checks the list's ids and levels against OWASP's files, and each "what it asks" is read against the requirement's own text. The answers are counted by a script from the list itself. **The rules the list found**, each gap's rule for Build, go into 11-checks; the list says when it's ticked by hand (before the first tester, again before launch) and which requirements wait for a later moment.
3. **The outside test before launch** (a pentest or not, with its price, against the free alternatives first: a ZAP active scan on our own staging, the list ticked by hand, a TLS test from outside, a disclosure policy, a bug bounty later), and **the triggers that bring a paid one back** (revenue, worked out against the price; a business customer; a big change; then yearly), the focused days before the full test; **the user decides**; what each slice's pass checks.

### 13. The big decisions become ADRs
Only one-way doors (for example the ASVS level with its written deviations, Row-Level Security if chosen, a key that is never rotated, the session model if not yet recorded). First propose the list, with **what doesn't get an ADR and why** (most numbers change easily; so do a no to Row-Level Security, the secrets manager, the pentest). **The user chooses**, one at a time. After each ADR, re-read the earlier files it changes, the earlier steps' included; the README names the ADRs decided before that shape the protections.

### 14. Check it
- every asset has its threats; every way in on the map appears in the model;
- every endpoint in `openapi.yaml` has an access rule (the script run again); every count in the README matches the files, `facts.py` run again;
- every threat has a protection or an accepted risk with its reason and who accepted it; every protection has its check; every threat not only accepted or transferred is named in a row of 11-checks; no id reused;
- every number has its source or is marked `[ASSUMPTION]`; every claim read at its source, with the date;
- every deviation is accepted in the README; every gap has its rule for Build and its slice;
- every question the earlier steps left for Security is answered (`left-for-security.sh` run again);
- no secret's value in any document;
- nothing contradicts the PRD, compliance, the architecture, the data model, the API or the UI design.

Run the check with a **separate agent** that has only the documents (`/security validate <folder>`), then verify its findings in the files before showing them: it can be wrong. Look especially for **contradictions left by a changed decision**, above all in files the step didn't touch. Tell the user upfront how long it usually takes (15–20 minutes) and that there's nothing for them to do meanwhile. Show the verified findings by severity with a recommendation; a rule that changes in another step's document is shown with its exact new text before it's written.

Write as you go: each step's file once the user confirms it, with a journal line in the README; **the README's summary, accepted risks and glossary grow with the steps**, not at the end. **Before calling the README done, read it against every file, last:** the counts against the scripts (addresses, flows, threats, secrets, accounts, alerts, protections, the list's answers); every summary bullet against its file and its ADR today; every accepted risk against its threat's decision and its check; "Next" and the status against the design's map. At the end, set this step's row in `docs/02-design/README.md` to done, with the date, and link the folder; each later date it's brought in line is added to the row, and it's checked again after every later change.

1. **Read** the slice's features, its endpoints, tables, files and providers, the threats of its flows, **the tries the README's open questions mark for this slice, the rules the list found that it carries**, and **what changed since Design** (the earlier slices, the journal).
2. **What's new or changed** (an endpoint, a table, a file type, a provider, a role) goes through STRIDE; new rows in the model with the next free ids, the user deciding any new accepted risk.

## Validate mode
`/security validate <folder>`: judge an existing threat model or security design, change nothing.
1. Read the folder, its ADRs and the README's journal, the PRD, compliance, the architecture, the data model, the API design (with `openapi.yaml`) and the UI design; the running app's headers and configuration if they exist.
2. Check the template and "Done when" item by item, citing the lines; run the access-rule script, the scripts in `checks/` and `facts.py`.
3. Then ask: is any way in missing from the map? Any endpoint without a rule, or with an id and no "is it yours?" test? Any threat without a check, or one not only accepted or transferred that no row of 11-checks names? Any id used twice? Any accepted risk without a reason, an owner or a revisit? Any deviation written as a gap, or a gap called closed because its rule is written? Any number without a source, any quote without its date, any requirement cited from another version than the list's? Any "tried" for a check that never ran, or a check never seen failing on a planted mistake? Any secret's value written? Any protection decided earlier and silently changed here? A journal in more than one voice? **Then the classic holes:** a second factor that can be added with the password alone; deploy secrets readable from any branch on the code host's plan; a limit counted on an IP the client can forge; an audit log the app can rewrite. **Then the decisions that changed during the steps:** is the old version still written anywhere, above all in files the step didn't touch?
4. Report: findings by severity, each with the line, what's wrong and what to change; then what's done well; then what you couldn't evaluate. The user picks what to apply.

## The bad version and why not
- Security "at the end", with a pentest as the only measure: it finds what it can in a few days; the rest stays, and the fixes touch code already built.
- The OWASP Top 10 ticked as a list of requirements: ten broad categories, not verifiable requirements; that's ASVS.
- Login or crypto written by hand: the framework has the version thousands of teams have tried.
- "Is it yours?" checked only in the app (a hidden button): the API can be called directly, with `curl`.
- A JWT in `localStorage`: any XSS steals it, and "sign me out everywhere" needs a list of blocked tokens.
- An account locked after 5 wrong passwords: anyone who knows the email can lock it; slow down instead.
- Composition rules and a password changed every 90 days: NIST forbids both; they produce "Password1!", then "Password2!".
- "This email already has an account": a list of addresses for phishing; on a health app, having an account is already information about a person.
- Secrets in the repository "because it's private": GitGuardian found plaintext secrets in 35% of its customers' private repositories.
- The app connected as the tables' owner: one SQL injection can drop them.
- Updates postponed "until things settle": in 2025, four years after Log4Shell, about 13% of ~300 million Log4j downloads still had it, and 95% of vulnerable components downloaded already had a fixed version (Sonatype, December 2025).
- Every new version taken in its first hour: each of TanStack's bad versions lived about 2 h 53 min to 4 h 35 min (May 2026); whoever installed them then ran them.
- A scanner trusted because it ran green: one that never caught a planted mistake may read nothing (a lockfile it can't parse reports no dependencies, without an error).
- A gap ticked off because its rule is written: it stays a gap until the code meets it.
- CI actions on a tag (`@v4`) with a token that can write everywhere: a tag can be moved to bad code.
- A request body logged "for debugging": passwords and health data at a log provider for weeks.
- A stack trace in an answer: a map of the code for the attacker.
- A CSP with `'unsafe-inline'` "to make it work": it no longer stops XSS.
- No second factor on the code host and the hosting provider: the shortest way to everything, without a single vulnerability in the code.
- An alert for everything: nobody reads them, not even the real one.

## What breaks if you skip it
Each protection is decided by the PR that needs it, and the numbers stay the framework's defaults: Spring Boot ends a session after 30 minutes unused, so people are signed out after every meal, and someone "fixes" it with a session of a year. The first tester puts their data into a system whose protections nobody tried together. The first leak is found by a user; with health data, the authority gets a description of it and of the measures within 72 hours (GDPR article 33), and GDPR asks measures "appropriate to the risk", tested regularly (article 32), not the ones thought of in a hurry.

## The principle behind it
**A protection is an assumption until it's tried, and never the only thing between an attacker and someone's data.** It comes from Saltzer and Schroeder (1975), the principles modern security rests on: **complete mediation** (check every access, every time: "is it yours?" on every request), **fail-safe defaults** (closed unless allowed), **least privilege** (each user and program gets only what it needs), **economy of mechanism** (the simplest protection, since a complicated one hides holes). And Microsoft's Zero Trust adds **assume breach**: design for the day a layer falls, not only so it doesn't.

## How to apply it at work
- At a new company: ask for the threat model; if there's none, run the four questions for an hour on the main flow; look at who can reach production, where the secrets live and when the dependencies were last updated.
- In code review, for a new endpoint: who may call it and where is that checked? What comes in unchecked? What reaches the log? Does "doesn't exist" answer like "isn't yours"? For a new library: who maintains it, since when, what does it run at install?
- With a customer's security questionnaire, ISO 27001 or SOC 2: the model, the inventory of secrets, the incident plan and the ASVS list answer most questions.
- When a critical vulnerability is published: the SBOM says in minutes whether you're affected; KEV and EPSS say how urgent it is.
- For a change, only the steps it touches, in a short design doc: **a new endpoint with an id:** its row in the map and the count run again, its STRIDE rows, its limit if it costs something, its "is it yours?" test, `no-store`, its events, its check and its ASVS lines in the slice's "done when"; **a new provider or key:** its flow on the redrawn map, its threats, its inventory row (what it opens, where it lives, who reads it, rotation, the hour it leaks), the fewest rights, an expiry, an IP restriction, a spend cap, its console's second factor checked on its page, its hosts in the CSP; **a new upload or file type:** its threats, the file typed by content, a size and pixel limit, re-encoded, a new name, private storage, the ASVS file requirements read again and any deviation it reopens (no antivirus holds only while every upload is an image); **a new third-party script:** what it could reach on your origin, where and when it loads, its hosts first in `Report-Only`, its flow on the map, the risk accepted by whom, PCI DSS 6.4.3 and 11.6.1 for a card form; **a new role or admin action:** the rule on its prefix, the role read from the database, a test sending the role in a body, the second factor it asks and how recent, its audit line and the alert for a new admin; **an incident:** the first hour's runbook, then a new threat row, its check and a journal line.
- As a senior or a CTO: a security champion in every team, ASVS in the definition of done, scanners in CI as a gate for "critical", a pentest every year and at every big change, a public disclosure policy, a second factor for everyone, access reviewed at every departure, a tabletop incident exercise a year, maturity measured with OWASP SAMM.
